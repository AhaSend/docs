Railway runs your app as a long-lived Node.js process, so the SDK works with no serverless or edge caveats. This guide deploys the [Express app](/guides/express); any Node.js framework ([Fastify](/guides/fastify), [Koa](/guides/koa), [NestJS](/guides/nestjs)) deploys the same way.

## Prerequisites

- A [Railway account](https://railway.com) and the [Railway CLI](https://docs.railway.com/guides/cli) installed, or a GitHub repo connected to the service
- Node.js 22 or later
- An [AhaSend account](https://dash.ahasend.com/user/register) with a verified sending domain
- An [API key](https://dash.ahasend.com/account/-/settings/api-keys) with the `messages:send:all` scope, and your account ID

## What You're Deploying

Any app that sends with the SDK, for example:

```ts server.ts
import { AhaSendClient } from "@ahasend/sdk";

const ahasend = new AhaSendClient({
 apiKey: process.env.AHASEND_API_KEY!,
 accountId: process.env.AHASEND_ACCOUNT_ID!,
});

// ...routes that call ahasend.messages.send({ from: { email: "hello@yourdomain.com" }, ... })
```

A send returns a **multi-status** result, one entry in `result.data` per recipient, and an individual recipient can come back with `status: "error"` and a null `id` (a suppressed address, for example) while the call itself succeeds, so check every entry: `const rejected = result.data.filter((r) => r.status === "error")`.

<Note>
Railway injects a `PORT` environment variable and routes public traffic to it. Make sure your server listens on it:

```ts
app.listen(Number(process.env.PORT) || 3000);
```
</Note>

## Pin the Node Version

The SDK requires **Node.js 22 or later**, and Railway's builder picks a default version if you don't say otherwise. Pin it explicitly by adding an `engines` field to `package.json`:

```json package.json
{
 "engines": { "node": ">=22" }
}
```

Nixpacks reads that field; you can also set `NIXPACKS_NODE_VERSION=22` as a service variable, or use a `FROM node:22-slim` base image if you deploy with a Dockerfile.

## Deploy

<Steps>
 <Step title="Create or link the project">
 ```bash
 railway init # new project
 # or, inside an existing project's repo:
 railway link
 ```
 </Step>
 <Step title="Set the variables">
 In the Railway dashboard, open your service and go to **Variables**, or use the CLI:

 ```bash
 railway variables --set "AHASEND_API_KEY=aha-sk-..." \
 --set "AHASEND_ACCOUNT_ID=your-account-uuid" \
 --set "AHASEND_WEBHOOK_SECRET=aha-whsec-..."
 ```

 Railway can **seal** a variable so its value can never be read back from the dashboard, a good fit for the API key. If several services need the same credentials, define them once as **shared variables** at the project level and reference them from each service.
 </Step>
 <Step title="Deploy">
 Push straight from your machine:

 ```bash
 railway up
 ```

 Or connect the GitHub repo in the service settings, and Railway builds and deploys on every push. Variable changes trigger a redeploy so the new values are picked up.
 </Step>
</Steps>

## Expose a Public Webhook URL on Railway

Your service is private by default. To receive AhaSend webhooks, generate a public domain: open the service, go to **Settings → Networking**, and click **Generate Domain**. Then create the webhook in your [AhaSend dashboard](https://dash.ahasend.com) pointing at:

```
https://your-app.up.railway.app/webhooks/ahasend
```

Because Railway processes are long-lived, the SDK's Express webhook adapter (see [Handle webhooks](/guides/express#handle-webhooks)) runs exactly as it does locally. On Express 5.x there's no raw-body setup at all: mount `expressWebhookHandler` directly on the route (no `express.raw({ type: "*/*" })`), since the adapter reads and bounds the raw stream itself. Just keep that route out of the reach of any global `express.json()`.

## Going Further

- **App-side detail**: the [Express guide](/guides/express) covers sends, per-recipient error handling, and the webhook adapter in full.
- **Client configuration**: see the [Node.js SDK guide](/guides/nodejs-sdk) for timeouts, retries, and idempotency options.
- **An alternative host**: [Vercel](/guides/vercel) runs the same SDK on serverless functions if you'd rather not manage a process.
- **Long-lived processes suit webhooks**: nothing is torn down between deliveries here, so background work after the 2xx keeps running, unlike on serverless.
- **Attachments**: pass `attachments: [{ data, content_type, file_name, base64: true }]`. Set `base64: true` for binary files such as PDFs.

## Troubleshooting

<AccordionGroup>
 <Accordion title="Deployment is live but the URL returns 502">
 The app isn't listening on Railway's assigned port. Bind to `process.env.PORT` (and host `0.0.0.0` if your framework asks for one).
 </Accordion>
 <Accordion title="401 AhaSendAuthenticationError in production">
 The variable is set on a different service or environment than the one that deployed. Check the service's **Variables** tab and confirm the latest deploy happened after you set them.
 </Accordion>
 <Accordion title="Webhook verification fails on Railway but works locally">
 `AHASEND_WEBHOOK_SECRET` must be copied exactly as shown in the AhaSend dashboard, including the `aha-whsec-` prefix. Watch for shells or quoting stripping characters when using `railway variables --set`.
 </Accordion>
</AccordionGroup>

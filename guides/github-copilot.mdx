The Copilot coding agent works out of sight and hands you a finished pull request. It cannot read your repository secrets and it cannot merge, which makes your review the only gate that matters.

If you came here looking for **Copilot Workspace**, the standalone issue-to-PR preview: it was retired in May 2025 and its flow now lives in the coding agent, which is the tool covered here.

## Prerequisites

The agent can write the integration, but it can't verify your domain or mint your credentials. Do that in the [AhaSend dashboard](https://dash.ahasend.com) first:

1. **Verify a sending domain.** Add the SPF, DKIM, and DMARC records from the [domain setup guide](/domains). AhaSend validates DNS continuously, so a misconfigured domain fails at send time rather than quietly tanking your deliverability.
2. **Create an API key.** Follow the [API credentials guide](/send-api/credentials) and scope it to `messages:send:{your-domain}` instead of `messages:send:all`, so a leaked key can only touch one domain's mail. Note your **account ID**.

Your deployed app reads the key from your hosting platform's secret store. If you want the agent to execute a send while it tests its own work, you also add a sandbox key to its `copilot` environment in Step 4.

The SDK requires Node.js 22 or later, so set the project's `engines` field and CI workflow to 22 before you hand the task over. The agent copies whatever the repo already declares.

## Step 2: Write the Issue

Put the real interface in the issue so the agent cannot invent a client library or hand-roll HTTP calls. Open an issue, describe the task in specifics, and assign it to Copilot:

> **Title:** Add order-confirmation email via AhaSend
>
> **Body:** When an order is created, send a confirmation email using the official AhaSend Node.js SDK, `@ahasend/sdk`, which is already a dependency. Do not hand-roll fetch calls and do not add any other email package.
>
> - Construct the client once at module scope in `lib/ahasend.ts`: `new AhaSendClient({ apiKey: process.env.AHASEND_API_KEY, accountId: process.env.AHASEND_ACCOUNT_ID })`.
> - Send with `client.messages.send({ from, recipients, subject, html_content, text_content })`. Body fields are snake_case.
> - The response is multi-status: `result.data` has one entry per recipient, and a recipient can come back `status: "error"` while the promise resolves. Check every entry, not just the first.
> - Catch `AhaSendAPIError` from `@ahasend/sdk` and match on `err.status`, never on message text.
> - Read `AHASEND_API_KEY` and `AHASEND_ACCOUNT_ID` from server-side environment variables. Never hardcode them and never expose them to the client.
> - Send from server-side code only (an API route or controller), never from the browser. The SDK throws if it detects an edge runtime.
> - Set `sandbox: true` in the send body so tests don't deliver real mail.

That issue rules out a hallucinated package, pins the constructor and the method, names the response shape, and states the security rule. The agent plans against those constraints and opens a PR that reflects them.

<Tip>
  To apply these rules to *every* task the agent picks up, put them in a `.github/copilot-instructions.md` file. The coding agent reads it as standing context, the same way it reads your tests, so "use the SDK, key stays server-side, check every recipient" becomes a default it carries into every email-related PR rather than something you retype each time.
</Tip>

## Step 3: Review the Pull Request

When the agent finishes, it requests your review. The agent can only push to branches named `copilot/*` and never merges to your default branch, so this review is the gate every change passes through. Read the diff with three questions in mind.

**Did the key stay server-side?** The integration should read `AHASEND_API_KEY` from the environment, in server-side code. Scan the diff for the opposite: a literal `aha-sk-...` string committed anywhere, or, if the agent touched a frontend, a key dropped into a client-exposed variable (anything like `NEXT_PUBLIC_`, `VITE_`, or a value referenced inside a browser component). If you see any of those, don't merge. Comment `@copilot move the AhaSend call to a server-side route and read the key from an environment variable, never expose it to the client`, and it'll push a correction to the same PR.

**Is it using the SDK, correctly?** A representative server-side route looks about like this:

```ts app/api/send-confirmation/route.ts
import { AhaSendClient, AhaSendAPIError } from "@ahasend/sdk";

const client = new AhaSendClient({
  apiKey: process.env.AHASEND_API_KEY!,
  accountId: process.env.AHASEND_ACCOUNT_ID!,
});

export async function POST(req: Request) {
  const { email, name, orderId } = await req.json();

  try {
    const result = await client.messages.send({
      from: { email: "orders@yourdomain.com", name: "Your Store" },
      recipients: [{ email, name }],
      subject: `Order ${orderId} confirmed`,
      text_content: `Thanks ${name}, order ${orderId} is confirmed.`,
      html_content: `<p>Thanks ${name}, order ${orderId} is confirmed.</p>`,
      sandbox: process.env.NODE_ENV !== "production",
    });

    const rejected = result.data.filter((r) => r.status === "error");
    if (rejected.length > 0) {
      console.warn(`${rejected.length} recipient(s) rejected`);
    }

    return Response.json({ statuses: result.data.map((r) => r.status) });
  } catch (err) {
    if (err instanceof AhaSendAPIError) {
      console.error(`AhaSend error ${err.status} (request ${err.requestId})`);
      return new Response("Failed to send email", { status: 502 });
    }
    throw err;
  }
}
```

Note the client at module scope, not inside the handler. A client constructed per request throws away connection reuse and retry state.

**Does it treat the response as multi-status?** A resolved promise means AhaSend accepted and queued the request, not that every address was accepted. `result.data` carries one entry per recipient, and a suppressed address comes back `status: "error"` with a null `id` while the call itself succeeds. If the PR reads `result.data[0]` and reports success, leave a comment and let the agent fix it before you merge. This bug survives a passing test, so check it by eye.

## Step 4: Give the Agent a Sandbox Key

The agent runs in a GitHub Actions environment and can execute code, including a real call to AhaSend, but only if you give it a key. It has no access to your repository or organization Actions secrets: the only secrets it sees are the ones you add to a GitHub Actions environment named `copilot`. Create (or open) that environment and add a **sandbox-mode AhaSend key** as `AHASEND_API_KEY`, plus `AHASEND_ACCOUNT_ID`.

Use a dedicated sandbox credential, not your production key. AhaSend lets you create a credential that is always in sandbox mode, so any send made with it is simulated regardless of the request body. With that key in the `copilot` environment, the agent can run an integration test that sends through the SDK, gets a real queued result back, and confirms the wiring end to end. Nothing is delivered and nothing is billed. Sandbox keys and the `sandbox_result` outcomes (`deliver`, `bounce`, `defer`, `fail`, `suppress`) are covered in the [sandbox mode guide](/send-api/sandbox).

<Warning>
  Never put your production API key in the `copilot` environment. The agent's logs and its pull request description are both places a key can end up in plain text.
</Warning>

Skip this step and the agent still writes correct code from the issue's constraints; you verify the first live send yourself after merging.

## Step 5: Merge and Send a Real Email

Once the diff passes the review checks and, if you set it up, the sandbox test is green, merge the `copilot/*` branch through your normal process. Then, in your real environment:

- Confirm `AHASEND_API_KEY` and `AHASEND_ACCOUNT_ID` are set in your **hosting platform's** secret store, not committed, and not in the `copilot` environment, which only ever held the sandbox key.
- Flip `sandbox` to `false`, ideally driven by an environment variable so you can toggle without another PR.
- Send one real confirmation to an address you control and confirm it arrives.

## Going Further

- **Make the sandbox part of CI**: a test that pins `sandbox_result` to `bounce` and `suppressed` turns "the agent says it handles failures" into something the pull request has to prove.
- **Templating and webhooks**: per-recipient `substitutions` handle personalised batches, and `@ahasend/sdk/webhooks` verifies delivery-event signatures. Put both in `.github/copilot-instructions.md` so the next issue starts from them.
- Same grounding trick, different file: [Cursor](/guides/cursor) reads `.cursor/rules/`, [Claude](/guides/claude) reads `CLAUDE.md`, and [Windsurf](/guides/windsurf) reads `.windsurf/rules/`.
- For the finished shape of the integration the agent is writing, see [Next.js](/guides/nextjs), [Express](/guides/express), or [Remix](/guides/remix).

## Troubleshooting

<AccordionGroup>
  <Accordion title="The agent's test run fails with a Node version error">
    The SDK declares `engines.node >= 22`. The agent's environment follows the repo, so set `engines.node` in `package.json` and pin Node 22 in your CI workflow's `actions/setup-node` step, then re-run the agent.
  </Accordion>
  <Accordion title="The PR hand-rolls fetch calls instead of using the SDK">
    Either the dependency wasn't committed to `main` before you opened the issue, or the issue didn't name the package. Comment `@copilot replace the raw fetch calls with the @ahasend/sdk client` and push the constraint into `.github/copilot-instructions.md` so the next task inherits it.
  </Accordion>
  <Accordion title="401 AhaSendAuthenticationError in the agent's run">
    The `copilot` Actions environment either doesn't have `AHASEND_API_KEY` or has a revoked one. Repository and organization secrets are deliberately invisible to the agent, so the key must live in that environment specifically.
  </Accordion>
  <Accordion title="The generated code throws on startup in an edge route">
    The SDK is Node-only and its constructor throws if it detects a browser, service worker, or edge runtime. Move the send to a Node runtime route, or call the REST API directly from the edge. See [Cloudflare Workers](/guides/cloudflare-workers) for that pattern.
  </Accordion>
</AccordionGroup>

Every endpoint the SDK exposes is in the [API reference](/api-reference).

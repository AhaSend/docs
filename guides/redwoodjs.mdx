In [RedwoodJS](https://redwoodjs.com) the SDK belongs in the `api` workspace only, so the key never reaches anything the browser downloads. The send goes in a service, the webhook is just another api-side function.

## Prerequisites

- Node.js 22 or later and a RedwoodJS v7/v8 project
- An [AhaSend account](https://dash.ahasend.com/user/register) with a verified sending domain
- An [API key](https://dash.ahasend.com/account/-/settings/api-keys) with the `messages:send:all` scope, and your account ID

## Install the SDK

The SDK belongs on the **api side** only, so install it into the `api` workspace:

<CodeGroup>

```bash yarn (Redwood default)
yarn workspace api add @ahasend/sdk
```

```bash npm
npm install @ahasend/sdk --workspace api
```

```bash pnpm
pnpm add @ahasend/sdk --filter api
```

```bash bun
bun add @ahasend/sdk --cwd api
```

</CodeGroup>

The SDK needs Node.js 22 or later, so make sure your api-side runtime and any `engines.node` field say `">=22"`.

## Configure Environment Variables

Add your credentials to the project's `.env`. The api side reads `process.env` directly, so no further configuration is needed:

```bash .env
AHASEND_API_KEY=aha-sk-...
AHASEND_ACCOUNT_ID=your-account-uuid
AHASEND_WEBHOOK_SECRET=aha-whsec-...
```

<Warning>
  Redwood's `includeEnvironmentVariables` setting in `redwood.toml` allowlists variables for the **web side**, baking them into the browser bundle. Never add any `AHASEND_*` variable there: the api side needs no allowlist and the key must stay server-only.
</Warning>

## Create the Client

Create the client once at module scope and reuse it across invocations:

```ts api/src/lib/ahasend.ts
import { AhaSendClient } from "@ahasend/sdk";

export const ahasend = new AhaSendClient({
  apiKey: process.env.AHASEND_API_KEY!,
  accountId: process.env.AHASEND_ACCOUNT_ID!,
});
```

## Send an Email from a Redwood Serverless Function

A Redwood function gives you a plain HTTP endpoint at `/.redwood/functions/sendWelcome` (or `/sendWelcome` on the api server):

```ts api/src/functions/sendWelcome.ts
import type { APIGatewayEvent } from "aws-lambda";
import { AhaSendAPIError } from "@ahasend/sdk";
import { ahasend } from "src/lib/ahasend";

export const handler = async (event: APIGatewayEvent) => {
  const { email, name } = JSON.parse(event.body ?? "{}");

  try {
    const result = await ahasend.messages.send({
      from: { email: "hello@yourdomain.com", name: "Your App" },
      recipients: [{ email, name }],
      subject: "Welcome to Your App!",
      html_content: "<h1>Welcome aboard 🎉</h1><p>We're glad you're here.</p>",
      text_content: "Welcome aboard! We're glad you're here.",
    });

    const rejected = result.data.filter((r) => r.status === "error");

    return {
      statusCode: 200,
      body: JSON.stringify({ queued: result.data.length - rejected.length, rejected }),
    };
  } catch (err) {
    if (err instanceof AhaSendAPIError) {
      console.error(`AhaSend error ${err.status} (request ${err.requestId})`, err.body);
      return { statusCode: 502, body: JSON.stringify({ error: "Failed to send email" }) };
    }
    throw err;
  }
};
```

A 202 is a **multi-status** response: `result.data` holds one entry per recipient, and an individual recipient can come back with `status: "error"` and a null `id` (a suppressed address, for example) while the call itself succeeds. Inspect every entry, not just the first.

The SDK retries transient failures automatically, but a retry after a 5xx can still send twice, so pass your own `idempotencyKey` when a duplicate would be expensive.

### Alternative: Send from a Service

If sending belongs to your GraphQL flow (say, after `createUser`), put the send in a service and call it from a mutation resolver: services are plain server-side functions, so the same client works:

```ts api/src/services/emails/emails.ts
import { ahasend } from "src/lib/ahasend";

export const sendWelcomeEmail = async ({
  email,
  name,
}: {
  email: string;
  name?: string;
}) => {
  const result = await ahasend.messages.send({
    from: { email: "hello@yourdomain.com", name: "Your App" },
    recipients: [{ email, name }],
    subject: "Welcome to Your App!",
    text_content: "Welcome aboard! We're glad you're here.",
  });
  const rejected = result.data.filter((r) => r.status === "error");
  return { queued: result.data.length - rejected.length, rejected };
};
```

Add `sandbox: true` to the send request to validate it without delivering anything.

## Handle Webhooks

Redwood functions use the Lambda-style event, which already carries the raw body as a string, exactly what signature verification needs. `verifier.parse()` is asynchronous as of 0.2.0, so await it. One catch: some providers deliver the body base64-encoded, so check `event.isBase64Encoded` and decode first:

```ts api/src/functions/ahasendWebhook.ts
import type { APIGatewayEvent } from "aws-lambda";
import { WebhookVerifier, isKnownWebhookEvent } from "@ahasend/sdk/webhooks";

const verifier = new WebhookVerifier(process.env.AHASEND_WEBHOOK_SECRET!);

export const handler = async (event: APIGatewayEvent) => {
  const rawBody = event.isBase64Encoded
    ? Buffer.from(event.body ?? "", "base64").toString("utf-8")
    : (event.body ?? "");

  let webhookEvent;
  try {
    webhookEvent = await verifier.parse(event.headers as Record<string, string>, rawBody);
  } catch {
    return { statusCode: 400, body: "" };
  }

  if (isKnownWebhookEvent(webhookEvent)) {
    switch (webhookEvent.type) {
      case "message.delivered":
        console.log(`Delivered to ${webhookEvent.data.recipient}`);
        break;
      case "message.bounced":
        console.log(`Bounced: ${webhookEvent.data.recipient}`);
        break;
      case "message.opened":
        console.log(`Opened by ${webhookEvent.data.recipient}`);
        break;
    }
  }

  return { statusCode: 200, body: "" };
};
```

Create the webhook in your [AhaSend dashboard](https://dash.ahasend.com) pointing at `https://your-app.com/.redwood/functions/ahasendWebhook`, and copy its secret into `AHASEND_WEBHOOK_SECRET` exactly as shown (including the `aha-whsec-` prefix).

## Going Further

- **Templating**: pass `substitutions` per recipient and use `{{ variable }}` in the subject or body.
- **Batch sends**: `recipients` accepts up to 100 entries; each gets a separate, individually-substituted message.
- **Scheduling**: set `schedule: { first_attempt: "2026-07-04T09:00:00Z" }` to defer delivery.
- **Your own idempotency keys**: pass `{ idempotencyKey: "order-123" }` as the second argument to `send()` to dedupe against your own identifiers.
- **Attachments**: pass `attachments: [{ data, content_type, file_name, base64: true }]`. Set `base64: true` for binary files such as PDFs.

See the [API reference](https://ahasend.com/docs/api-reference) for every endpoint the SDK exposes. Redwood functions use the Lambda event shape, so the [AWS Lambda guide](/guides/aws-lambda) applies almost verbatim when you deploy there; for a plain Node server instead, see the [Express guide](/guides/express).

## Troubleshooting

<AccordionGroup>
  <Accordion title="Webhook verification always returns 400">
    Most often the body was base64-encoded by the provider: check `event.isBase64Encoded` and decode with `Buffer.from(event.body, "base64")` before calling `verifier.parse()`, as shown above. Also confirm `AHASEND_WEBHOOK_SECRET` includes the `aha-whsec-` prefix.
  </Accordion>
  <Accordion title="401 AhaSendAuthenticationError">
    The API key is missing, malformed, or revoked. Verify `AHASEND_API_KEY` is in `.env` (restart `yarn rw dev` after editing it) or set in your deploy provider's environment, and that the key exists in your [dashboard](https://dash.ahasend.com/account/-/settings/api-keys).
  </Accordion>
  <Accordion title="Variable undefined on the web side">
    That's by design. Do not fix it by adding `AHASEND_*` keys to `includeEnvironmentVariables`, which would embed them in the browser bundle. Email must always go through the api side (a function or service).
  </Accordion>
  <Accordion title="400 error mentioning the from address">
    The `from` address must belong to a verified sending domain on your account. Check domain status in the dashboard.
  </Accordion>
</AccordionGroup>

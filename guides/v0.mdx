[v0](https://v0.app) thinks in client components, and a client component is the one place an API key can never live. Drawing that boundary is the work here, because v0 will not draw it for you.

## Prerequisites

- Node.js 22 or later, set as the Node.js version in your Vercel project settings
- A v0 project connected to a Vercel deployment
- An [AhaSend account](https://dash.ahasend.com/user/register) with a [verified sending domain](/domains)
- An [API key](/send-api/credentials) with a send scope, plus your account ID

Verify the domain and create the key in the [dashboard](https://dash.ahasend.com) first: the [quickstart](/quickstart) walks through both. Scope the key to `messages:send:{your-domain}` rather than `messages:send:all`, so a leak exposes one domain's outbound mail instead of your whole account.

## Add the Key as a Server-Side Vercel Variable

<Warning>
If v0 already put your key in a `NEXT_PUBLIC_` variable or referenced it from a client component, treat it as leaked. Delete the variable, rotate the key in the dashboard, and only then continue.
</Warning>

In your Vercel project, open **Settings → Environment Variables** and add:

```bash
AHASEND_API_KEY=aha-sk-...
AHASEND_ACCOUNT_ID=your-account-uuid
```

No `NEXT_PUBLIC_` prefix on either. Vercel encrypts them at rest and exposes them only to server-side code at runtime. Add the variables to the **Production** and **Preview** environments, not just Development, then **redeploy**. Vercel injects environment variables at build time, so a variable added after your last deploy reads back as `undefined` until you ship again.

## Create the Client

Create the client once at module scope and reuse it. It keeps its own connection pooling, retry, and idempotency state, which a fresh client per request throws away:

```ts lib/ahasend.ts
import { AhaSendClient } from "@ahasend/sdk";

export const ahasend = new AhaSendClient({
 apiKey: process.env.AHASEND_API_KEY!,
 accountId: process.env.AHASEND_ACCOUNT_ID!,
});
```

## Ask v0 for a Route Handler

Name the architecture in the prompt, or v0 reaches for the client. The phrase that does the work is *Route Handler*:

> "Add a Next.js Route Handler at `app/api/send-email/route.ts` that sends a confirmation email with the `@ahasend/sdk` package. Export `const runtime = "nodejs"`. Import the shared client from `lib/ahasend.ts`, which reads `AHASEND_API_KEY` and `AHASEND_ACCOUNT_ID` from `process.env`. These are server-only, never `NEXT_PUBLIC_`. The form component must POST to `/api/send-email`; it must never call AhaSend directly and must never reference the API key."

What v0 generates should land close to this:

```ts app/api/send-email/route.ts
import { NextResponse } from "next/server";
import { AhaSendAPIError } from "@ahasend/sdk";
import { ahasend } from "@/lib/ahasend";

export const runtime = "nodejs"; // the SDK does not run on the Edge runtime

export async function POST(request: Request) {
 const { email, name } = await request.json();

 try {
 const result = await ahasend.messages.send({
 from: { email: "hello@yourdomain.com", name: "Your App" },
 recipients: [{ email, name }],
 subject: "You're all set",
 html_content: `<p>Thanks ${name}, your account is confirmed.</p>`,
 text_content: `Thanks ${name}, your account is confirmed.`,
 sandbox: true, // flip to false when you're ready to send for real
 });

 const rejected = result.data.filter((r) => r.status === "error");
 return NextResponse.json({
 queued: result.data.length - rejected.length,
 rejected,
 });
 } catch (err) {
 if (err instanceof AhaSendAPIError) {
 console.error(`AhaSend error ${err.status} (request ${err.requestId})`);
 return NextResponse.json({ error: "Failed to send email" }, { status: 502 });
 }
 throw err;
 }
}
```

Check two details in review. The key is read from `process.env` inside a Route Handler, so it stays on the server and never enters the bundle. And the response is **multi-status**: AhaSend answers a send with HTTP 202 because it has accepted and queued the message, not finished delivering it, and `result.data` carries one entry per recipient. An individual recipient can come back `status: "error"` with a null `id`, a suppressed address for example, while the promise still resolves. Check every entry, not just the first.

The SDK retries transient failures (408, 429, 5xx, network, timeout) with exponential backoff and attaches an idempotency key to every send. Stored outcomes replay for 24 hours, but a 5xx is not stored, so a retry after one can still send twice.

## Call the Route from the Form

Have v0 build the form to POST to your route:

```tsx components/signup-form.tsx
const res = await fetch("/api/send-email", {
 method: "POST",
 headers: { "Content-Type": "application/json" },
 body: JSON.stringify({ email, name }),
});
```

No key, no AhaSend URL, no Bearer token: the browser talks to your own route, and only your route talks to AhaSend.

## Test in Sandbox Mode

Keep the `sandbox: true` above while you build. In sandbox mode AhaSend runs your message through the full validation and queuing pipeline, fires every webhook, and logs it in your dashboard, then stops just short of delivery. It costs nothing and it cannot email a real person by accident.

Rehearse the failures too. Add `sandbox_result: "bounce"` to simulate a hard bounce, or `"defer"`, `"fail"`, and `"suppress"` for the rest, and confirm your route handles each. The full set is in the [sandbox mode guide](/send-api/sandbox). Then read the flag from an environment variable so you can switch without editing code, and send one real test to an address you control.

## Audit Before You Ship

The mistake this guide prevents is invisible in the preview, so run one deliberate check.

<Steps>
 <Step title="Search the repo for the key">
 No `aha-sk-` string and no `NEXT_PUBLIC_AHASEND...` variable anywhere in client code. The key should exist only as a server-side Vercel variable, read only in server code. If v0 slipped it into either, that value is already public: remove it and rotate the key.
 </Step>
 <Step title="Confirm the form posts to your route">
 The form POSTs to `/api/send-email`, not to `api.ahasend.com`. The browser hits your route; only the route hits AhaSend.
 </Step>
 <Step title="Redeploy after adding variables">
 Otherwise `process.env.AHASEND_API_KEY` is `undefined` and every send returns 401.
 </Step>
</Steps>

## Going Further

- **Templating**: pass `substitutions` per recipient and use `{{ variable }}` in the subject or body.
- **Batch sends**: `recipients` accepts up to 100 entries, each of which gets its own message.
- **Webhooks**: the SDK's `nextRouteHandler` verifies signatures for you. The [Next.js guide](/guides/nextjs) has the full setup.
- **Deployment details**: the [Vercel guide](/guides/vercel) covers environment variable scoping, the Node.js runtime requirement, and function limits.
- Building in a different AI tool? See [Lovable](/guides/lovable) and [Bolt.new](/guides/bolt-new).

See the [API reference](/api-reference) for every field and endpoint the SDK exposes.

## Troubleshooting

<AccordionGroup>
 <Accordion title="Error about window, document, or node:crypto on deploy">
 The route is running on the Edge runtime, which the SDK does not support. Add `export const runtime = "nodejs"` to every route that imports `@ahasend/sdk`. If a route must stay on the Edge, call the REST API with `fetch` from there instead.
 </Accordion>
 <Accordion title="process.env.AHASEND_API_KEY is undefined in production">
 The variable was added after the last deploy, or only to the Development environment. Add it to Production and Preview, then redeploy.
 </Accordion>
 <Accordion title="API key visible in the browser bundle">
 You prefixed the variable with `NEXT_PUBLIC_`. Rename it to `AHASEND_API_KEY`, rotate the leaked key in the dashboard, and read it only from server code.
 </Accordion>
 <Accordion title="400 error mentioning the from address">
 The `from` address must belong to a verified sending domain on your account. Check domain status in the dashboard.
 </Accordion>
</AccordionGroup>

Sending transactional email with Bun needs no shims: [Bun](https://bun.sh) implements `node:crypto` and `node:buffer`, so the AhaSend SDK runs on it as-is. Install it, point `Bun.serve` at a fetch handler, and you're sending in a few minutes.

## Prerequisites

- Bun 1.0 or later
- An [AhaSend account](https://dash.ahasend.com/user/register) with a verified sending domain
- An [API key](https://dash.ahasend.com/account/-/settings/api-keys) with the `messages:send:all` scope, and your account ID

## Install the SDK

```bash
bun add @ahasend/sdk
```

[`@ahasend/sdk`](https://www.npmjs.com/package/@ahasend/sdk) is still v0.x, so the API may change before 1.0: pin the exact version in production (`bun add @ahasend/sdk@0.1.0`). The package declares `engines.node >= 22`; Bun provides the Node built-ins it needs.

## Configure Environment Variables

Add your credentials to `.env`:

```bash .env
AHASEND_API_KEY=aha-sk-...
AHASEND_ACCOUNT_ID=your-account-uuid
AHASEND_WEBHOOK_SECRET=aha-whsec-...
```

<Note>
Bun loads `.env` automatically, no `dotenv` package or `--env-file` flag needed. The variables are available on `process.env` (and `Bun.env`) as soon as your script starts.
</Note>

<Warning>
The API key grants full send access to your account. Keep it server-side, never ship it in a browser bundle.
</Warning>

## Create the Client

Create the client once at module scope and reuse it across requests: it maintains its own retry and idempotency state:

```ts lib/ahasend.ts
import { AhaSendClient } from "@ahasend/sdk";

export const ahasend = new AhaSendClient({
  apiKey: process.env.AHASEND_API_KEY!,
  accountId: process.env.AHASEND_ACCOUNT_ID!,
});
```

<Tip>
If you prefer pure env-driven configuration, `AhaSendClient.fromEnv()` builds a client from the `AHASEND_*` variables directly.
</Tip>

## Send an Email from a Bun.serve Route

`Bun.serve` with a fetch handler is all the HTTP server you need:

```ts server.ts
import { AhaSendAPIError } from "@ahasend/sdk";
import { ahasend } from "./lib/ahasend";

Bun.serve({
  port: 3000,
  async fetch(req) {
    const url = new URL(req.url);

    if (req.method === "POST" && url.pathname === "/api/welcome") {
      const { email, name } = await req.json();

      try {
        const result = await ahasend.messages.send({
          from: { email: "hello@yourdomain.com", name: "Your App" },
          recipients: [{ email, name }],
          subject: "Welcome to Your App!",
          html_content: "<h1>Welcome aboard 🎉</h1><p>We're glad you're here.</p>",
          text_content: "Welcome aboard! We're glad you're here.",
        });

        const rejected = result.data.filter((r) => r.status === "error");
        if (rejected.length > 0) console.warn(`${rejected.length} recipient(s) rejected`);

        return Response.json({ statuses: result.data.map((r) => r.status) }); // ["queued"]
      } catch (err) {
        if (err instanceof AhaSendAPIError) {
          console.error(`AhaSend error ${err.status} (request ${err.requestId})`, err.body);
          return Response.json({ error: "Failed to send email" }, { status: 502 });
        }
        throw err;
      }
    }

    return new Response("Not found", { status: 404 });
  },
});
```

Run it with `bun run server.ts`. A 202 is **multi-status**: `result.data` carries one entry per recipient, and an individual recipient can come back `status: "error"` with a null `id` (a suppressed address, say) while the call itself succeeds, so check every entry, not just the first.

The SDK automatically retries transient failures (408, 429, 5xx, network errors) with exponential backoff and attaches an idempotency key to every send. Stored outcomes replay for 24 hours, but a 5xx is not stored, so a retry after a 5xx can still send twice. Local rate-limit pacing is a separate, opt-in feature (`rateLimit: { enabled: true }`) that is off by default.

<Note>
Testing without delivering real mail? Add `sandbox: true` to the send request: the API validates and accepts it, but nothing leaves the platform.
</Note>

## Handle Webhooks

There's no Bun-specific adapter, and you don't need one: `verifier.parse()` accepts a Fetch `Headers` object and a raw body string directly, which is exactly what a Bun `Request` gives you. Read the body with `req.text()`, not `req.json()`, so the verifier sees the exact bytes AhaSend signed.

```ts server.ts
import { WebhookVerifier, isKnownWebhookEvent } from "@ahasend/sdk/webhooks";

const verifier = new WebhookVerifier(process.env.AHASEND_WEBHOOK_SECRET!);

// inside the fetch handler:
if (req.method === "POST" && url.pathname === "/webhooks/ahasend") {
  let event;
  try {
    event = verifier.parse(req.headers, await req.text());
  } catch {
    return new Response("Invalid signature", { status: 400 });
  }

  if (isKnownWebhookEvent(event)) {
    switch (event.type) {
      case "message.delivered":
        console.log(`Delivered to ${event.data.recipient}`);
        break;
      case "message.bounced":
        console.log(`Bounced: ${event.data.recipient}`);
        break;
      case "message.opened":
        console.log(`Opened by ${event.data.recipient}`);
        break;
    }
  }

  return new Response(null, { status: 200 });
}
```

Create the webhook in your [AhaSend dashboard](https://dash.ahasend.com) pointing at `https://your-app.com/webhooks/ahasend`, and copy its secret into `AHASEND_WEBHOOK_SECRET` exactly as shown (including the `aha-whsec-` prefix).

## Going Further

- **Templating**: pass `substitutions` per recipient and use `{{ variable }}` in the subject or body.
- **Batch sends**: `recipients` accepts up to 100 entries; each gets a separate, individually-substituted message.
- **Scheduling**: set `schedule: { first_attempt: "2026-07-04T09:00:00Z" }` to defer delivery.
- **Your own idempotency keys**: pass `{ idempotencyKey: "order-123" }` as the second argument to `send()` to dedupe against your own identifiers.

See the [API reference](https://ahasend.com/docs/api-reference) for every endpoint the SDK exposes (`client.domains`, `client.suppressions`, `client.statistics`, and more). Prefer a framework on top of Bun? The [ElysiaJS guide](/guides/elysiajs) uses the same SDK with typed routes.

## Troubleshooting

<AccordionGroup>
  <Accordion title="401 AhaSendAuthenticationError">
    The API key is missing, malformed, or revoked. Bun only auto-loads `.env` from the directory you run `bun` in. If you start the server from a subdirectory, the file won't be picked up. Log `process.env.AHASEND_API_KEY?.slice(0, 8)` to confirm it's loaded.
  </Accordion>
  <Accordion title="Webhook verification fails with 400">
    Make sure you pass `await req.text()` to `verifier.parse()`, not a re-serialized `JSON.stringify(await req.json())`: re-serialization changes key order and whitespace, so the signature no longer matches.
  </Accordion>
  <Accordion title="400 error mentioning the from address">
    The `from` address must belong to a verified sending domain on your account. Check domain status in the dashboard.
  </Accordion>
  <Accordion title="SDK works locally but you plan to deploy to an edge platform">
    The SDK relies on `node:crypto` and `node:buffer`. Bun provides both, but Cloudflare Workers and other edge runtimes don't. See the [Cloudflare Workers guide](/guides/cloudflare-workers) for the REST-API approach there.
  </Accordion>
</AccordionGroup>

[Bolt.new](https://bolt.new) runs your app in a browser-based WebContainer, so the preview cannot make the send you are testing. Code that looks fine there can still fail, or publish your API key, the moment you deploy.

## Prerequisites

- A Bolt project, with Supabase connected or a Node server target chosen
- An [AhaSend account](https://dash.ahasend.com/user/register) with a [verified sending domain](/domains)
- An [API key](/send-api/credentials) with a send scope, plus your account ID

Set the AhaSend side up in the [dashboard](https://dash.ahasend.com) before Bolt writes a line: the [quickstart](/quickstart) covers domain verification and key creation. Scope the key to `messages:send:{your-domain}` instead of `messages:send:all` so a leaked key can only touch one domain's mail.

## Pick Your Backend

Two rules apply whichever shape your project takes. Never call AhaSend from the frontend or from a client-side Supabase hook: that ships your API key to the browser, where any visitor can read it out of your JavaScript. And put the key where the send runs, not where the site is served. Bolt Hosting and Netlify settings configure your *frontend* host, so a key set there is invisible to a Supabase Edge Function.

<Warning>
  If Bolt already put the key in a `VITE_`-prefixed variable or referenced it from a client component, that value is public. Remove it and rotate the key in the dashboard before you continue.
</Warning>

Bolt projects end up in one of two shapes, a Supabase Edge Function or a Node server, and [`@ahasend/sdk`](https://www.npmjs.com/package/@ahasend/sdk) runs on both. Use it either way. What differs is only where the key lives:

| Your backend | Where the key goes |
| --- | --- |
| Supabase Edge Function (Deno) | Supabase secrets, read with `Deno.env.get()` |
| Node server (Express, Fastify, Nitro, deployed to a Node host) | That host's environment variables, read from `process.env` |

Supabase Edge Functions run on Deno, so they need SDK 0.2.0 or later, which is where Deno and edge runtime support landed. On Node hosts the SDK needs Node.js 22 or later.

## Send with the SDK

Install the SDK, which handles retries, idempotency, and typed errors:

<CodeGroup>

```bash npm
npm install @ahasend/sdk
```

```bash pnpm
pnpm add @ahasend/sdk
```

```bash bun
bun add @ahasend/sdk
```

</CodeGroup>

In a Supabase Edge Function there is nothing to install: Deno resolves the package from the import specifier, `import { AhaSendClient } from "npm:@ahasend/sdk"`.

If you are on Supabase, add your credentials as Supabase secrets, not Bolt or Netlify variables:

```bash
supabase secrets set AHASEND_API_KEY=aha-sk-your-key
supabase secrets set AHASEND_ACCOUNT_ID=your-account-uuid
```

The Supabase dashboard does the same under your project's Edge Functions settings. These are encrypted and injected only into your Edge Functions at runtime. On a Node host, set the same two variables in that host's environment settings.

Name the architecture in the prompt, or Bolt reaches for a client-side hook:

> "Add a backend endpoint called `send-receipt` that emails an order confirmation with the `@ahasend/sdk` package. Read `AHASEND_API_KEY` and `AHASEND_ACCOUNT_ID` from the server environment and pass them to `new AhaSendClient()` at module scope. Treat HTTP 202 as success. The frontend must call this endpoint, it must never call AhaSend directly and must never contain the API key."

Create the client once at module scope, then send:

```ts server/email.ts
import { AhaSendClient, AhaSendAPIError } from "@ahasend/sdk";

const ahasend = new AhaSendClient({
  apiKey: process.env.AHASEND_API_KEY!,
  accountId: process.env.AHASEND_ACCOUNT_ID!,
});

export async function sendReceipt(email: string, name: string, orderId: string) {
  try {
    const result = await ahasend.messages.send({
      from: { email: "orders@yourdomain.com", name: "Your Store" },
      recipients: [{ email, name }],
      subject: `Order ${orderId} confirmed`,
      html_content: `<p>Thanks ${name}, order ${orderId} is confirmed.</p>`,
      text_content: `Thanks ${name}, order ${orderId} is confirmed.`,
      sandbox: true,
    });

    return result.data.filter((r) => r.status === "error");
  } catch (err) {
    if (err instanceof AhaSendAPIError) {
      console.error(`AhaSend error ${err.status} (request ${err.requestId})`);
      return null;
    }
    throw err;
  }
}
```

Inside a Supabase Edge Function the code is the same, except that Deno has no `process.env`: read the two secrets with `Deno.env.get("AHASEND_API_KEY")` and `Deno.env.get("AHASEND_ACCOUNT_ID")` and pass them to the constructor, then call `sendReceipt` from your `Deno.serve` handler.

Full framework setup lives in the [Express](/guides/express) and [Next.js](/guides/nextjs) guides.

## Handle the 202 Response

Success is **202**, not 200: AhaSend has accepted and queued your message for asynchronous delivery. A handler that expects 200 reports failures that did not happen.

The 202 body is multi-status: it carries one result per recipient. An individual recipient can come back `status: "error"` with a null `id`, a suppressed address for example, while the request succeeded and the promise resolves. Inspect every entry, not just the first.

## Test in Sandbox Mode

The WebContainer preview cannot prove your email works, and once you deploy, the first time your code can reach AhaSend it can also reach a real inbox. Keep `sandbox: true` in the body and AhaSend accepts the message, validates it, fires every webhook, and logs it in your dashboard, then stops just before delivery. That gives you a real round-trip to the API confirmed by a real 202, with nothing landing in an inbox while you iterate.

Rehearse the failures too. Add `sandbox_result: "bounce"` to simulate a hard bounce, or `"defer"`, `"fail"`, and `"suppress"` for the rest, and check your code handles each. The full set is in the [sandbox mode guide](/send-api/sandbox).

## Deploy and Verify the Key

Your deployed backend and frontend live in different homes. Before you call it done:

<Steps>
  <Step title="Search for the key in frontend code and host settings">
    No `aha-sk-` string anywhere in the frontend, and no AhaSend variable in Bolt Hosting or Netlify settings unless that host is also running your Node backend. The key belongs where the send runs.
  </Step>
  <Step title="Confirm the browser calls your backend">
    The frontend calls your Edge Function or your Node route; only that backend talks to `api.ahasend.com`.
  </Step>
  <Step title="Flip sandbox off deliberately">
    Read the flag from a secret or environment variable so you can switch without editing code, then send one real test to an address you control.
  </Step>
</Steps>

## Going Further

- **Templating**: pass `substitutions` per recipient and use `{{ variable }}` in the subject or body.
- **Batch sends**: `recipients` accepts up to 100 entries, each of which gets its own message.
- **Idempotency**: pass your own key as `{ idempotencyKey: "order-123" }`, the second argument to `send()`, so a double-click cannot send twice. Stored outcomes replay for 24 hours, but 5xx outcomes are not stored.
- Building in a different AI tool? See [v0](/guides/v0) and [Lovable](/guides/lovable). See the [API reference](/api-reference) for every field.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Error importing @ahasend/sdk in a Supabase Edge Function">
    You are on an SDK version older than 0.2.0, which is where Deno and edge runtime support landed. Upgrade to 0.2.0 or later and redeploy the function.
  </Accordion>
  <Accordion title="undefined API key at runtime">
    The key was set on the frontend host instead of where the send runs. For an Edge Function, use `supabase secrets set` and redeploy the function afterward.
  </Accordion>
  <Accordion title="The send works in the preview but not after deploy">
    The WebContainer preview and the deployed app are different environments with different secrets. Check that the deployed backend has the secrets set, then look at the dashboard logs: a message that never reached AhaSend leaves no log line.
  </Accordion>
  <Accordion title="400 error mentioning the from address">
    The `from` address must belong to a verified sending domain on your account. Check domain status in the dashboard.
  </Accordion>
</AccordionGroup>
